# 法律 RAG 问答系统

从国家法律法规数据库抓取法条，构建可检索的知识库，回答问题并给出**可逐条核验的引用**。

和直接问大模型的区别：答案只依据检索到的条文生成，引用会被校验是否真的出现在资料里；
检索不到时系统说"资料不足以确定"，而不是凭记忆编一段像模像样的答案。

## 效果

### 检索增益的梯度实验

同一套代码、同一个模型、同一批判分，**只替换语料库**，看 RAG 相对"模型凭记忆回答"的增益：

| 语料 | 条数 | 检索 recall@5 | 无 RAG | 有 RAG | 净收益 |
|---|---|---|---|---|---|
| 民法典 | 1260 | 99.0% | 95.0% | 99.0% | **+4.0pp** |
| 4 部司法解释 | 244 | 100.0% | 52.0% | 100.0% | **+48.0pp** |
| 2026 年新颁法律 | 1298 | 100.0% | 7.0% | 100.0% | **+93.0pp** |

新法是 2026-03 和 2026-08 颁布的，在模型知识截止之后。无 RAG 时引用正确率 7.0%，有 RAG 时 100.0%。

**净收益 = 检索天花板 − 模型记忆。** 增益随语料被模型内化的程度递减，但三个语料都为正。
民法典之所以增益最小，是因为模型对它已经足够熟（95%）——拿它证明"RAG 有用"没有说服力，
拿它证明"RAG 在什么条件下没用"才有。

### 检索消融

n=100 / 语料，全部开启查询改写，数字为 recall@1 / @5 / @10：

| 语料 | dense | dense+rerank | hybrid | hybrid+rerank |
|---|---|---|---|---|
| 民法典 | 87.0 / 94.0 / 100 | 88.0 / **98.0** / 100 | **91.0 / 99.0** / 100 | 89.0 / 98.0 / 100 |
| 司法解释 | 90.0 / 100 / 100 | **93.0** / 97.0 / 99.0 | 92.0 / 100 / 100 | **93.0** / 97.0 / 100 |
| 新法 | 90.0 / 100 / 100 | **94.0** / 100 / 100 | 92.0 / 100 / 100 | **94.0** / 100 / 100 |

### 组件结论

| 组件 | 结论 |
|---|---|
| **查询改写** | 收益最大。口语问题与法条字面几乎不重合，改写补上法律术语后才能被检索到 |
| **hybrid（dense + BM25）** | 保留。两路的失败模式互补：dense 擅长"换个说法"，BM25 擅长专有名词 |
| **rerank** | 换用 `bge-reranker-v2-m3` 后不再有害，但收益落在噪声范围内，且 CPU 上约 20 秒/题。**产品默认不挂** |
| **合并索引** | 保留。代价主要出现在语义重叠的法之间（司法解释与民法典讲同一件事，@5 −4pp） |

### 多跳检索：单轮的边界在哪

上面所有实验用的题都是**单条法条就能回答**的。当问题需要 2~3 条法条配合时：

| | 单跳题 | **多跳题** |
|---|---|---|
| `hit_all@5`（多条全部命中才算中） | 99~100% | **34.0%** |
| `hit_any@5`（至少中一条） | — | 92.0% |

`hit_any` 高达 92% 但 `hit_all` 只有 34% —— **单轮不是找不到，是找不全**：它稳稳捞到第一跳，第二跳就丢了。

多跳评测集有两套，配对依据强弱不同：一套是同一部法内跨章随机配对（100 题，覆盖广）；
另一套**按司法解释正文里显式写着的"民法典第X条"配对**（35 题，依据是法条自己声明的），
用来交叉验证前一套的结论不是出题方式造成的假象。

### 多轮检索

在检索前加一个循环：捞一轮 → 让模型判断还缺什么 → 换个查询再捞。

| | 累计条数 | `hit_all` |
|---|---|---|
| 单轮 k=5 | 5.0 | 34.0% |
| 多轮第 2 轮 | 7.4 | 58.0% |
| 多轮第 3 轮 | 8.6 | **61.5%** |

**同尺寸对照**（多轮累计 8.6 条，就拿单轮 k=9 来比）：单轮 43.0% → 多轮 **61.5%，+18pp**。
换个说法更直观：**多轮用 8.6 条达到 61.5%，单轮塞 10 条才 47%。**

> **运行间波动 ±2.9pp**（重复 4 次：64 / 58 / 60 / 64）。循环里有个 LLM，每次生成的查询都不一样，
> **单次运行的数字不能直接引用**，必须重复运行。第 1 轮是完全确定的（每次都是 34.0%，一位不差）。

提升能传导到答案——端到端引用覆盖率：

| | 检索覆盖 | 答案覆盖 |
|---|---|---|
| 单轮 | 0.62 | 62.3% |
| 多轮 | 0.80 | **78.3%** |

**答案覆盖率 ≈ 检索覆盖率**，多跳场景下瓶颈依然全在检索，生成环节没有损耗。

### 引用可核验性

系统的设计前提是"答案只依据检索到的条文生成、引用可逐条核对"。这个性质在 200 道题上量过：

| | 多跳集（n=100） | 新法集（n=100） |
|---|---|---|
| 引用全部能在资料里找到 | 100.0% | 100.0% |
| 出现编造引用 | **0.0%** | **0.0%** |

最极端的一格：**在一条正主都没捞到的 8 道题上，编造率仍是 0** —— 模型没有拿记忆去填补检索的空白。

> ⚠️ **但这个 0% 测的不是校验器，是提示词。** 提示词里写着"只能依据资料回答"，
> 模型照做了，校验器根本没被触发。校验器是**提示词失效时的兜底**，它的正确性由
> `tests/test_citation_validate.py` 单独验证 —— 主动喂已知的坏引用，看能不能抓出来。
>
> 那个测试第一次跑就红了：原来的判据把**条号**和**法名**分成两个集合各自判断，
> 于是"资料里是《生态环境法典》第一条、模型引《民法典》第一条"两关都过。
> 合并库里"第一条"在 7 部法里都有，这个漏洞会让错误引用显示成"✓ 可核验"。
> 改成按 **(法名, 条号) 这一对**判断后 8/8 通过。

## 快速开始

### 环境

- Python 3.10+（开发环境 3.13）
- 无需 GPU。rerank 在 CPU 上可跑，只是慢（约 20 秒/题）

### 安装

```bash
git clone <repo-url>
cd legal_RAG
pip install -r requirements.txt

# PyTorch 用 CPU 版即可
pip install torch --index-url https://download.pytorch.org/whl/cpu
```

模型权重首次运行会自动从 HuggingFace 下载（约 400MB + 2.2GB）。
国内网络建议设置镜像：

```bash
export HF_ENDPOINT=https://hf-mirror.com
export HF_HUB_DISABLE_XET=1     # 镜像不代理 Xet 协议，不设会 401
```

Windows 用 `setx HF_ENDPOINT https://hf-mirror.com`，设完需要重开终端。

### 配置 API key

问答和查询改写调用 DeepSeek 的 Anthropic 兼容接口。key 的读取顺序是
环境变量 `DEEPSEEK_API_KEY` → `data/api_key.txt`，后者只存一行 key 本身。

```bash
echo "sk-xxxxxxxx" > data/api_key.txt   # 该文件已在 .gitignore 中
```

### 生成向量索引

`*_vectors.npy` 是二进制产物，不进仓库（见 `.gitignore`）。但 `*_chunks.jsonl`
是提交过的，所以**不需要重新抓取和清洗**，跑一遍 embedding 即可：

```bash
python data/embed.py                        # 民法典
python data/law_pipeline.py embed sfjs      # 司法解释
python data/law_pipeline.py embed new       # 新法
python data/merge_index.py                  # 合并成 all_*
```

四步合计约 1 分钟（CPU）。

### 跑起来

```bash
python app.py
# 打开 http://127.0.0.1:8000
```

页面上的语料库、召回条数、检索模式、是否改写都可以实时切换，会显示检索依据和引用校验结果。

### 命令行

```bash
python src/answer.py 高空抛物砸到人该找谁赔
python src/answer.py --corpus new --no-rewrite 医保个人账户能不能给家人用
python src/retrieve.py --mode hybrid 高空抛物砸到人该找谁赔
```

## 数据管道

```
抓取 → 清洗 → 分块 → 向量
```

**数据源**：`flk.npc.gov.cn`（国家法律法规数据库）。

### 两种分块路径

民法典和司法解释/新法的 OFD 渲染格式不同，走了两条路径：

| 语料 | 脚本 | 特点 |
|---|---|---|
| 民法典 | `clean_pages.py` → `clean_toc.py` → `clean_reflow.py` → `chunk.py` | 条号独立成行，正文在下一行 |
| 司法解释 / 新法 | `law_pipeline.py` | 条号与正文粘在同一行，按"行首是否第X条"切分 |

`chunk.py` 用状态机读取"编/章/节"标题来维护层级上下文，按**条**切块而不是按字数——
条是自足规范单元，也是法律引用的天然粒度。

`law_pipeline.py` 是通用版，换一部法只需要改文件顶部的 `SETS` 配置。

### 校验闸门

每个阶段跑完先校验，不合格直接退出：

- 条文数是否符合官方条号区间
- 是否有空正文
- 条号是否连续

## 评测

### 评测集

每部法 100 题，共 300 题。60 道"口语化"（普通人会怎么问）+ 40 道"法条原话"（律师式问法）。

题目由 `make_eval.py` 从条文反向生成候选，再由 `filter_eval.py` 自动筛选：
剔除泄题（问题里出现条文原文片段）、重复、过长过短的题，并按题型 6:4、按法等比分配配额。

### 检索评测

```bash
python src/eval_recall.py --sweep                 # 民法典
python src/eval_recall.py --sweep laws            # 司法解释
python src/eval_recall.py --sweep new             # 新法
python src/eval_recall.py --rerank --rewrite new  # 含 rerank 的完整扫描
python src/eval_recall.py --sweep laws --index all  # 同一批题改用合并库
```

判定口径：一题命中@k = 它的标准条号出现在检索结果前 k 条里。
合并库下还会连法律名一起比对（"第一条"在 7 部法里都存在）。

### 端到端评测

```bash
python src/eval_answer.py --no-rag                              # 无 RAG 基线
python src/eval_answer.py --dense --rewrite --retr hybrid       # 有 RAG
```

判定口径：模型给出的**唯一**引用，指向的条文是标准条号。

多轮运行的结果追加在 `data/评测结果.jsonl`。

### 多跳评测

```bash
# 生成与筛选
python data/make_multihop_eval.py 120 data/多跳_候选.jsonl          # 随机跨章配对
python data/make_crossref_eval.py                                  # 按司法解释显式引用配对
python data/filter_multihop.py <候选> <chunks> <输出> <题量>

# 检索侧（hit_all@k）
python src/eval_multihop.py --eval data/多跳评测集.jsonl --sweep --rewrite
python src/eval_multihop.py --mode bm25 --rewrite --agentic --rounds 3 --k 5

# 端到端（引用覆盖率 / 全中率 / 多引率）
python src/eval_multihop_answer.py --eval data/多跳评测集.jsonl --mode bm25
python src/eval_multihop_answer.py --eval data/多跳评测集.jsonl --mode bm25 --agentic
```

判定口径是 `hit_all@k`（多条全部命中才算中），不是 `recall@k` —— 一题有多个标准答案时，
后者会把"差一条"和"一条没中"混成一样，而这两种失败的治法完全不同。

**指标局限（已知）**：`全中率` 要求引用集合完全等于金标，但金标不是穷尽的 ——
它只是生成时从一束条文里挑出的那 2~3 条，题目可能还合理涉及别的条文。
所以"多引"里有一部分其实是对的，被这个指标误判。**主指标应看 `引用覆盖率`，`全中率` 只作参考。**

## 关键设计

**按条分块，条号单独存字段。** 条是法律引用的天然粒度；条号是评测的对照键，不能被揉进正文。

**多法语料必须连法名一起比对。** 只比条号会产生大量假命中。

**查询改写是前置条件而非可选项。** 口语问题与法条字面几乎不重合，不开改写时检索质量显著下降。
改写 prompt 里禁止输出条号，代码层再机械剥离一遍，避免模型把答案写进查询里污染评测。

**引用校验。** 模型给出的引用必须出现在喂给它的资料中，否则标记为"引用存疑"。
检索失败时系统输出"资料不足以确定"并说明理由。

**串联组件的强度关系。** rerank 的价值取决于它比粗排强多少：早期使用的
`bge-reranker-base`（约 110M）弱于粗排，加了反而全线变差；换成 `bge-reranker-v2-m3`
（约 568M）后不再有害。

**评测指标宁可严不可松。** 最初判定"标准条号在引用集合中即算正确"，模型一次列 6 条
法条即可全中，指标失去区分度。改为"只认唯一引用 + 精确匹配"后才有意义。

## 已知限制

1. **单语料样本量仍偏小。** n=100 时 95% 置信区间半宽约 ±5.9pp，几个百分点的差异
   不具统计显著性。要可靠检出 5pp 差异需要约 300 题/语料。
2. **多跳题的金标不穷尽。** 金标只是生成时从一束条文里挑出的那 2~3 条，题目可能还合理
   涉及别的条文，所以 `全中率` 会低估（见「多跳评测」一节的指标局限）。
3. **多跳评测集的配对依据强弱不一。** 交叉引用那套有法条文本支撑，随机跨章那套只是模型
   判断 —— 后者得出的结论都要用前者交叉验证过才能用。
4. **循环式检索的运行间波动未经充分刻画。** 只重复了 4 次（得到 ±2.9pp），样本偏少；
   且波动来自 LLM 生成查询的随机性，不是可以直接算出来的统计量。
5. **评测题存在自举偏差。** 题目由模型从条文反向生成，用词可能贴近原文。但无 RAG 条件下
   模型看不到条文，因此对比仍然公平，偏差方向偏保守。
6. **rerank 在 CPU 上约 20 秒/题**，且只吃满物理核心，多进程也无法加速。生产环境需换 GPU
   或更小的模型。
7. **分块只到"条"**，未做"款"级父子块。
8. **尚无自动化测试**，验证依赖各脚本内置的校验闸门。
